# /debug — 系统性调试

按以下四阶段排查问题。**铁律：没有完成 Phase 1 根因调查前，不能提出修复。**

## Phase 1: 根因调查

1. **读错误信息** — 完整阅读 stack trace、错误码、文件路径、行号
2. **复现** — 找到可靠触发步骤。不能稳定复现 → 收集更多数据，不要猜
3. **检查近期变更** — `git diff`、最近 commits、新增依赖、配置变化
4. **收集多组件证据** — 如果是多层系统，在每层边界加诊断日志，运行一次收集证据
5. **追踪数据流** — 坏值从哪里来？谁传进来的？一直追溯到源头

## Phase 2: 模式分析

1. **找对标成功案例** — 同代码库中类似的、正常工作的代码
2. **完整阅读参考实现** — 不要跳读
3. **列出所有差异** — 工作 vs 不工作的每个差异点

## Phase 3: 假设与验证

1. **形成单一假设** — "我认为 X 是根因，因为 Y"
2. **最小变更验证** — 单变量测试
3. **验证后继续** — 成功 → Phase 4；失败 → 形成新假设
4. **3 次修复都失败** → 质疑架构，不要继续修

## Phase 4: 实施修复

1. **先写失败测试** — 复现 bug
2. **单一修复** — 只改变根因
3. **验证** — 测试通过？无回归？

## 红旗信号（必须停下回到 Phase 1）

- "Quick fix for now, investigate later"
- "Just try changing X and see if it works"
- "It's probably X, let me fix that"
- 同时改多处的冲动
- 跳过写测试的冲动
